# AP FRQ Tutor Spec

> **Status:** Proposed. This specification must be reviewed before implementation.
>
> **Scope:** AP Calculus AB and AP US History SAQ only. All other AP courses are
> content entry once the pipeline is validated with these two.

---

## 1. Diagnosis

### What is actually needed

An AP Free Response Question tutor that gives the student an FRQ under a timer,
accepts a photo of their handwritten work or typed text, transcribes it, grades
it point-by-point against a structured rubric, and saves the result to Firestore
for a progress view.

The core technical claim is that one grading pipeline can handle both symbolic
math (Calculus AB) and prose writing (US History SAQ) without course-specific
grading logic. If it works for both, every other AP course is content entry.

### The grading rule that defines the product

The model never generates a score directly. It works through the rubric point by
point. For every rubric point it must return:

- **earned** or **not earned**
- The exact piece of the student's work that earned it (quoted back)
- If not earned, what specifically was missing

The score is the sum of earned points. It is never generated by the model. This
is what separates this from a generic "grade my essay" tool.

### Where it fits

The AP section lives under `korah-bot/ap/` as a peer to `korah-bot/sat/`. It
reuses:

- `api/r.js` for AI calls (Gemini proxy, already supports image content parts)
- `app/timer-manager.js` for timestamp-based timing that survives navigation
- `korah.css` and `sat.css` for design tokens, card patterns, and button styles
- `guest-gate.js` for signed-out handling and the `korahReady` event pattern
- `sidebar.html` for navigation (add AP Practice section)
- The Firestore pattern from `sat/js/sat-analytics.js` under `users/{uid}/`

It does not reuse or modify the SAT question player, analytics, or XP system.
This is a separate module with its own data.

### Expected scope

The work adds:

- 4 HTML pages (course picker, FRQ picker, attempt/feedback, progress)
- 1 CSS file (only what the shared files do not cover)
- 4 JS modules (bank loader, attempt controller, grader, progress)
- 2 JSON data files (one per course, with 8 FRQs each)
- A new sidebar section
- A new Firestore collection: `users/{uid}/apAttempts/{autoId}`
- A scraping notes doc

It does not add:

- A new API route (uses existing `/api/r`)
- Firebase Storage (photos are discarded after grading)
- A new Firebase emulator configuration
- React, a build step, or any framework

### How we will know it is done

1. A student can pick AP Calculus AB, select a specific FRQ, and see the prompt.
2. The timer starts and counts down (and past zero, recording time spent).
3. The student types a response (or photographs handwritten work).
4. The transcription is shown and can be corrected before grading.
5. The grader returns point-by-point verdicts against the structured rubric.
6. The score is the sum of earned points, never a directly generated number.
7. The student can flag any rubric point as disputed.
8. The attempt saves to Firestore and appears in Progress.
9. The Progress page shows score trends per course and rubric-category weakness.
10. An official sample response that scored full marks scores full marks through
    the pipeline. An official low-scoring sample misses the same points the
    official commentary identifies.
11. Every page renders its full UI with sidebar, navigation, and empty states
    when Firebase and `/api/r` are both unavailable (localhost testing).

## 2. Product goals

### Primary goal

Help an AP student practice FRQs under realistic conditions, get trustworthy
point-by-point feedback, and see which rubric categories they keep losing
points on.

### Supporting goals

- Prove one pipeline handles both math (symbolic, unambiguous rubric) and
  prose (fuzzy, contextual rubric).
- Build student trust by quoting their own work back at them for each verdict.
- Surface pacing data (time spent vs. time allotted) as a free signal.
- Make the weakness view the payoff, not just a list of past attempts.
- Keep the entire UI testable locally with placeholder data.

### Non-goals (for this version)

- Scoring DBQs, LEQs, or full-length essays (rubrics are harder to score
  reliably; short-form first).
- Other AP courses beyond Calculus AB and US History SAQ.
- Handwriting quality or penmanship feedback.
- Generating new FRQs or rubrics from College Board descriptions.
- Storing the student's photo (discard after transcription).
- Making the timer hard-lock at zero.
- Predicting an AP exam score from practice data.

## 3. User experience

### Entry points

A new "AP Practice" section in the sidebar, between SAT Practice and any other
section. Links:

- **AP Dashboard** (`ap/index.html`) - course picker
- **Progress** (`ap/progress.html`) - attempt history and weakness view

### System flow

```
Course picker (index.html)
  -> FRQ picker (frqs.html)
    -> Pre-attempt screen (attempt.html, pre-timer state)
      -> Attempt screen (attempt.html, timer running, prompt visible)
        -> Submit (photo upload or typed text)
          -> Transcription review (student confirms or corrects)
            -> Grading (per rubric point verdicts -> score -> feedback -> sample response)
              -> Saved to Firestore
                -> Shows up in Progress
```

### Page 1: Course picker (`ap/index.html`)

Displays available AP courses as cards. For the initial build, exactly two:

- **AP Calculus AB** - short, symbolic rubric points
- **AP US History** - prose, SAQ format only

Each card shows:

- Course name
- Number of available FRQs
- Number of attempted FRQs (0 when no Firestore)

Clicking a card navigates to `ap/frqs.html?course=ap-calculus-ab`.

### Page 2: FRQ picker (`ap/frqs.html`)

Loads FRQs for the selected course from the JSON data file. Displays a list with
each FRQ showing:

- Year and question number (e.g. "2023 FRQ 1")
- Topic or subject area
- Time allotted (e.g. "15 minutes")
- Calculator allowed badge (for Calc) or "No calculator"
- Attempted badge if the student has already done this FRQ (from Firestore, or
  absent when guest)

Clicking an FRQ navigates to
`ap/attempt.html?course=ap-calculus-ab&frqId=calc-ab-2023-q1`.

### Page 3: Attempt and feedback (`ap/attempt.html`)

This is the main page. It has multiple states managed by JS, not separate
HTML files.

#### State 1: Pre-attempt

- FRQ prompt and any stimulus (charts, graphs, source documents) displayed
- Time allotted shown
- Calculator allowed/not indicator
- "Start attempt" button
- If typed-input course, note that they can type below or work on paper

#### State 2: Active attempt

- Timer running (from `KorahTimer`), counting down from the allotted time
- Timer runs past zero, does not hard-lock. Records `timeSpentSec`.
- FRQ prompt and stimulus remain visible at all times
- For typed-input courses: a text area for typing the response
- For photo-input courses: the text area is present but the primary path is
  "Submit photos" button
- "Submit" button always available (does not require timer to be running)
- Time display shows elapsed or remaining, with visual indicator when past
  allotted time

#### State 3: Submission

- For photo input:
  - File picker accepting images (capture from camera or gallery)
  - Supports multiple pages (multi-image upload)
  - Client-side downscaling before upload (target: under 1MB per image,
    hard cap at 4.5MB total payload to `/api/r`)
  - Reject blurry or tiny images with a clear message before sending
  - Show image previews with page numbers, option to reorder or remove
- For typed input:
  - The typed text from the attempt state is carried forward
  - No image processing needed

#### State 4: Transcription review

- Vision model reads the uploaded images and produces a text transcription
- The transcription is displayed in an editable text area
- The original images are shown alongside so the student can compare
- "Confirm and grade" button
- "Edit" is always available, the student can fix any misread text
- This step exists because vision models misread math notation (subscripts,
  integrals, crossed-out work, arbitrary page layout). Showing the student
  what was read prevents the worst failure mode: losing a point because the
  model misread correct work.

#### State 5: Grading (loading)

- "Grading your response..." with an estimated wait (20-40 seconds)
- No skeleton or fake progress, just a clean loading state

#### State 6: Feedback

Three sections, displayed in order:

**A. Rubric ledger**

Each rubric point is a row showing:

- Point ID (internal, for tracking)
- Criterion text from the rubric
- Verdict: earned (green) or not earned (red)
- The student's work quoted back (the exact text that justified the verdict)
- If not earned: what was missing, written in plain language
- "I disagree" button on every point (flags for review, our only quality signal)

The score is displayed at the top as a simple sum:
"Score: 5 out of 6"

**B. One prioritized thing to fix**

A single sentence identifying the most impactful improvement. Not a list, not
an essay. One thing.

**C. Sample response comparison**

The official sample response shown side by side with the student's confirmed
transcript. The student can see how a full-marks response was structured.

#### State 7: Post-feedback

- "Try another FRQ" link back to the FRQ picker
- "View in Progress" link to the progress page
- "I disagree with this point" on each rubric point is still clickable

### Page 4: Progress (`ap/progress.html`)

#### Aggregate view (primary)

- Score trend per course (line chart or compact bar view)
- Total attempts per course
- Average score per course
- Rubric category weakness view: groups rubric points by category, shows
  which categories the student consistently loses points on
- Each category shows: category name, total points available across attempts,
  total points earned, accuracy percentage

#### Attempt list (secondary)

- Each past attempt as a row: FRQ name, date, score, time spent vs. allotted
- Clicking an attempt reopens the feedback view (read-only, no re-grading)

## 4. Data shapes

### FRQ JSON structure

Each course has a JSON file under `ap/data/{course-slug}/frqs.json`. The file
is an array of FRQ objects.

```json
{
  "id": "calc-ab-2023-q1",
  "course": "ap-calculus-ab",
  "year": 2023,
  "questionNumber": 1,
  "title": "Traffic Flow Analysis",
  "topic": "Definite Integrals",
  "timeAllottedMin": 15,
  "calculatorAllowed": true,
  "stimulus": {
    "type": "text",
    "content": "A traffic engineer studies the flow rate..."
  },
  "prompt": "The velocity of a car is modeled by v(t) = ...",
  "parts": [
    {
      "label": "(a)",
      "text": "Write a definite integral expression for the total distance traveled.",
      "rubricPoints": [
        {
          "id": "1a-integral-setup",
          "criterion": "Sets up the definite integral with correct limits of integration",
          "category": "integral-setup",
          "commonErrors": ["swapped limits", "missing dt", "using antiderivative notation instead of integral"],
          "exampleEarning": "Correctly writes integral from 0 to 8 of v(t) dt",
          "exampleFailing": "Writes v(8) - v(0) without integral notation"
        }
      ]
    }
  ],
  "sampleResponse": "The total distance is the integral from 0 to 8 of |v(t)| dt..."
}
```

For AP US History SAQ, the structure is the same but:

- `stimulus` is a source document (text, possibly with an image)
- `parts` contain prose-based rubric points
- `calculatorAllowed` is always false
- `rubricPoints` use categories like "contextualization", "evidence",
  "analysis", "claim"

#### Rubric point categories

Categories are course-specific and stable. They become the weakness groupings
in the Progress view.

**AP Calculus AB categories:**

- `integral-setup` - setting up integrals correctly
- `evaluation` - computing the integral or derivative
- `interpretation` - explaining what the result means in context
- `justification` - showing work and reasoning
- `units` - correct units on final answers
- `notation` - proper mathematical notation throughout

**AP US History SAQ categories:**

- `claim` - makes a clear, responsive claim
- `evidence` - provides specific historical evidence
- `analysis` - explains how evidence supports the claim
- `contextualization` - connects to broader historical context
- `completeness` - addresses all parts of the question

### Attempt document (Firestore)

Collection: `users/{uid}/apAttempts/{autoId}`

```json
{
  "frqId": "calc-ab-2023-q1",
  "course": "ap-calculus-ab",
  "confirmedTranscript": "The total distance traveled is...",
  "rubricVerdicts": [
    {
      "rubricPointId": "1a-integral-setup",
      "earned": true,
      "evidence": "Writes integral from 0 to 8 of v(t) dt",
      "feedback": null
    },
    {
      "rubricPointId": "1b-evaluation",
      "earned": false,
      "evidence": null,
      "feedback": "Computes the antiderivative but evaluates at wrong limits"
    }
  ],
  "score": 5,
  "totalPoints": 6,
  "timeAllottedSec": 900,
  "timeSpentSec": 1320,
  "disputedPoints": ["1b-evaluation"],
  "createdAt": "2026-09-07T14:30:00.000Z"
}
```

Rules:

- JSON primitives only, ISO date strings, no Firestore Timestamp objects.
- Store the confirmed transcript, not the photo.
- Discard the image after transcription. Never re-run the vision call on
  a re-grade.
- `disputedPoints` is an array of rubric point IDs the student flagged.
- `timeSpentSec` can exceed `timeAllottedSec` (timer ran past zero).

### Grading response shape (what ap-grader.js returns)

```json
{
  "verdicts": [
    {
      "rubricPointId": "1a-integral-setup",
      "earned": true,
      "evidence": "Student wrote: 'integral from 0 to 8 of v(t) dt'",
      "feedback": null
    },
    {
      "rubricPointId": "1b-evaluation",
      "earned": false,
      "evidence": null,
      "feedback": "Evaluated the antiderivative at t=8 and t=0, but swapped the subtraction order, resulting in a negative value for distance."
    }
  ],
  "score": 5,
  "totalPoints": 6,
  "priorityFix": "Review how you evaluate definite integrals after finding the antiderivative. Remember F(b) - F(a), not F(a) - F(b).",
  "sampleResponseComparison": "Your response focused on the algebraic setup but skipped the interpretation. The sample response explicitly states that the integral represents the total distance because velocity is non-negative on [0, 8]."
}
```

This shape is what the grader prompt produces. The `ap-grader.js` module parses
it, validates every `rubricPointId` against the FRQ's rubric, and computes the
score as a sum of earned verdicts. If the model returns a score that does not
match the sum, the computed sum wins.

## 5. Technical architecture

### AI pipeline: transcription

1. Student uploads one or more images.
2. Client-side: downscale each image to fit under 1MB (use canvas resize).
   Check minimum dimensions (reject images under 200px on any axis).
   Check for excessive blur (variance of Laplacian below threshold).
3. Send all images in a single `/api/r` call as `image_url` content parts
   (base64 data URIs). The endpoint already converts these to Gemini
   `inlineData`.
4. System prompt instructs the model to produce a faithful text transcription,
   preserving the student's structure (paragraph breaks, part labels, equation
   layout as best as possible).
5. Response is displayed in an editable text area for the student to confirm
   or correct.

### AI pipeline: grading

1. The confirmed transcript is sent to `/api/r` along with the structured
   rubric for the selected FRQ.
2. System prompt instructs the model to evaluate the response against each
   rubric point and return the grading response shape (verdicts array, score,
   priority fix, sample comparison).
3. `response_format: { type: "json_object" }` is used to enforce JSON output.
   The endpoint already supports this (maps to Gemini's `application/json`
   response MIME type).
4. `ap-grader.js` validates the response:
   - Every rubric point ID in the FRQ's rubric must appear in the verdicts.
   - The score must equal the count of `earned: true` verdicts.
   - If validation fails, the computed score overrides the model's score.
5. The validated result is displayed in the feedback UI and saved to Firestore.

### AI prompts

**Transcription system prompt (sketch):**

```
You are reading a student's handwritten or typed response to an AP Free
Response Question. Produce a faithful text transcription of their work.
Preserve paragraph breaks, part labels (a), (b), (c), and mathematical
notation using LaTeX where possible. If you cannot read a section clearly,
mark it with [illegible] rather than guessing. Do not interpret, correct,
or improve the student's work. Transcribe exactly what is written.
```

**Grading system prompt (sketch):**

```
You are grading an AP Free Response Question response against an official
scoring rubric. For each rubric point, determine whether the student earned
it based on their work. Return your evaluation as JSON matching this schema:
[verdicts schema]. For each point:
- earned: true only if the student's work clearly satisfies the criterion
- evidence: quote the exact portion of the student's work that justifies
  your verdict
- feedback: if not earned, explain specifically what was missing

Never generate a score directly. The score is the count of earned verdicts.
If the student's work is ambiguous, err on the side of not earning the point
and explain why it is ambiguous.

After all verdicts, provide:
- priorityFix: the single most impactful improvement
- sampleResponseComparison: how the student's response differs from the
  official sample response
```

The exact prompts will be refined during implementation. These sketches
establish the contract.

### Timer

Reuse `KorahTimer` from `app/timer-manager.js`. The AP attempt page calls:

```js
KorahTimer.start(timeAllottedMin)
```

When the timer fires completion, the UI shows a visual indicator but does not
lock. The student can continue working. `KorahTimer.getRemainingSeconds()` will
return negative values after the allotted time, which is the desired behavior.

On submit, the time spent is calculated as:

```js
const timeSpentSec = timeAllottedMin * 60 - KorahTimer.getRemainingSeconds()
```

This works whether the student submitted early or late.

### Image handling

Client-side downscaling before sending to `/api/r`:

1. Load image into an `<img>` element.
2. Draw onto a `<canvas>` with scaled dimensions.
3. Target: longest edge under 2000px, JPEG quality 0.8.
4. Export as base64 data URI.
5. Check file size: reject if over 4.5MB after downscaling.
6. Check minimum dimensions: reject if either axis under 200px.

Blur detection (optional but recommended):

1. Draw the image to a small canvas (150x150).
2. Convert to grayscale.
3. Apply a Laplacian-like variance check.
4. If variance is below a threshold (tuned during testing), warn the student
   that the image may be too blurry to read accurately.

### Firestore writes

After grading, `ap-progress.js` writes:

```js
await addDoc(collection(db, 'users', uid, 'apAttempts'), {
  frqId,
  course,
  confirmedTranscript,
  rubricVerdicts,
  score,
  totalPoints,
  timeAllottedSec,
  timeSpentSec,
  disputedPoints: [],
  createdAt: new Date().toISOString()
});
```

Follows the Korah pattern: JSON primitives, ISO strings, no Timestamp objects.

### Placeholder data strategy

Every page must render its full UI without Firebase or `/api/r`. This matches
the existing Korah contract (see `korah-bot/sat/index.html` on localhost: renders
complete, data does not fill in).

Concrete placeholder artifacts:

1. **Sample FRQ with real rubric** - checked into `ap/data/`, so the picker
   and attempt screen render with real content locally.
2. **Canned grading response** - a saved JSON blob shaped exactly like the
   grading response. Behind a flag or "no API key" fallback in `ap-grader.js`,
   return this instead of calling `/api/r`. This builds and styles the entire
   feedback screen without API calls.
3. **Canned transcription result** - same idea for the transcription review step.
4. **Fake past attempts** - a small array of mock attempt documents so the
   Progress page and weakness view have data to draw before Firestore is wired.

Follow the `guest-gate.js` pattern: `startGuestSession()` installs a stub
`window.KorahDB` (empty reads, dropped writes, fires `korahReady`). The AP
pages wait on `korahReady` before rendering, same as the rest of the site.

## 7. FRQ content sourcing

### Where FRQs come from

Every FRQ, rubric, and sample response must be extracted from College Board's
released free response question archive at `apcentral.collegeboard.org`. This is
a PDF-to-JSON task, same kind of job as the SAT practice test extraction in
issue #29.

### What to extract per FRQ

1. Prompt text (exact wording)
2. Any stimulus (charts, graphs, source documents, images)
3. Official scoring guidelines broken into individual rubric points
4. Sample responses (full marks and low-scoring, where available)
5. Time allotted and calculator permission

### Authoring standards

- Each rubric point gets a stable `id` (e.g., `calc-ab-2023-q1-1a-setup`).
  These IDs are referenced in Firestore documents and the Progress weakness
  view. They must not change after first use.
- Each rubric point gets a `category` from the course's category list. This
  is what the weakness view groups by.
- `commonErrors` captures what students typically do wrong for each point.
  This feeds the grader's understanding of what "not earned" looks like.
- `exampleEarning` and `exampleFailing` are concrete descriptions of what
  each looks like. These go into the grading prompt as few-shot guidance.
- Budget 30-60 minutes per FRQ to author the rubric properly. This is the
  slow part and the part that makes the product good.

### Initial scope

- AP Calculus AB: 8 FRQs (2019-2023, varying question numbers)
- AP US History SAQ: 8 SAQs (2019-2023, varying question numbers)

Math and science FRQs may have figures and equations. PNG is acceptable for
stimulus images, SVG is preferred. Store stimulus images under the course's
`data/` directory.

## 8. Build order

### Phase 1: Content and data (no UI)

Scrape and structure 2 FRQs by hand (one Calc, one US History). No UI. Just the
JSON with rubric points, categories, and sample responses. This is where we find
out what is hard about authoring structured rubrics.

Checkpoint: The JSON is reviewed, rubric points are stable, categories are
decided.

### Phase 2: Grader (no UI)

Build `ap-grader.js` in isolation. Feed it a typed response and the rubric, get
back point-by-point verdicts. Test against official sample responses:

- A sample that scored 6/6 must score 6/6 through the pipeline.
- A sample that scored low must miss the same points the official commentary
  identifies.

Work entirely with typed input and canned API responses. No photos, no
transcription.

Checkpoint: Grader produces correct verdicts for both courses against official
samples.

### Phase 3: Attempt screen (typed input only, placeholder data)

Full UI build with:

- Course picker and FRQ picker wired to the JSON data
- Timer running on the attempt screen
- Typed text input for the response
- Canned grading response displayed in the feedback view
- Transcription review step (skipped for typed input, but the DOM and state
  exist)
- All pages rendering on localhost with sidebar, navigation, empty states

Checkpoint: A student can pick an FRQ, type a response under a timer, submit,
and see point-by-point feedback. Everything runs on placeholder data.

### Phase 4: Photo upload and transcription

- Image picker, multi-page support, client-side downscaling
- Blur and size validation
- Transcription call to `/api/r` with images
- Transcription review step with editable text and image comparison
- "Confirm and grade" flow that feeds the transcript into the grader

Checkpoint: A student can photograph handwritten work, correct the
transcription, and get the same point-by-point feedback.

### Phase 5: Progress

- Firestore write after grading
- Progress page with attempt list
- Score trend per course
- Rubric category weakness view (group by category, compute accuracy)
- Wired to real Firestore reads/writes

Checkpoint: A student can see all past attempts, their trend, and which
rubric categories they keep losing points on.

## 9. Design direction

### Visual stance

The AP section should look like part of Korah's existing tools, not a separate
product. Reuse:

- Dark star background and shared sidebar
- `--sf`, `--bd`, `--tx` token system from `korah.css`
- Card patterns from `sat.css`
- Purple primary accent (`--p4`)
- Plus Jakarta Sans typography
- KaTeX for math rendering (Calculus AB rubrics and responses)

### Specific UI patterns

**Course picker cards:** Match the SAT dashboard card style. Solid surfaces,
subtle borders, no decorative gradients or glass effects on the cards themselves.

**FRQ list:** Rows inside a bordered list, similar to the Tailored Practice
priority list. Year, topic, time, calculator badge, attempted badge.

**Attempt screen:** Modeled on `sat/questions.html` and `sat-player.js`. Top
bar with timer, main content area with prompt, bottom bar with submit action.
Do not reinvent the player layout.

**Feedback rubric ledger:** Each rubric point as a row with earned/not-earned
status, quoted evidence, and feedback. Green/red indicators. "I disagree"
button as a subtle text button on each row.

**Progress weakness view:** A compact table or list grouping rubric categories
with accuracy bars. Not a chart library, just styled divs with width percentages.

### What not to add

- No em dashes in user-facing copy (Korah convention)
- No decorative gradients, glass effects, or hover lifts on cards
- No new fonts
- No chart libraries (use CSS for any visualization)
- No React, no build step

## 10. Open questions

These should be resolved before or during implementation, not deferred:

1. **Transcription accuracy for math:** How does Gemini 2.5 Flash handle
   integral notation, superscripts, and crossed-out work in photos? The
   transcription review step mitigates this, but we should test early in
   Phase 1.

2. **Grading consistency:** Will the same response graded twice produce the
   same verdicts? Temperature 0 helps, but we should run a consistency check
   during Phase 2.

3. **Rubric point granularity for US History:** Calc rubric points are
   unambiguous (integral set up correctly or not). History rubric points involve
   judgment calls. How fine-grained should the categories be? Too fine and the
   weakness view becomes noise. Too coarse and it loses signal.

4. **Multi-page photo ordering:** When a student uploads 3 pages, does order
   matter? For Calc it does (work builds on itself). For History less so. Should
   we require the student to arrange pages, or try to detect order from content?

5. **Rate limiting:** Each attempt consumes 2 API calls (transcription + grading).
   The current rate limit is 20 requests per 60 seconds per IP. This should be
   fine for individual use but could be a problem in a classroom setting. Do we
   need a separate rate limit for AP attempts?

6. **"I disagree" handling:** Where do disputed points go? Firestore flag for
   manual review? A simple counter? The spec says "our only quality signal" but
   does not define what happens with it.

7. **Stimulus images for Calc FRQs:** Some FRQs include graphs or figures. These
   need to be stored as image files and displayed in the prompt. Where do they
   live in the file structure, and how are they referenced from the JSON?

## 11. Firestore schema summary

```
users/{uid}/
  apAttempts/{autoId}
    frqId: string              "calc-ab-2023-q1"
    course: string             "ap-calculus-ab"
    confirmedTranscript: string
    rubricVerdicts: array      [{rubricPointId, earned, evidence, feedback}]
    score: number              5
    totalPoints: number        6
    timeAllottedSec: number    900
    timeSpentSec: number       1320
    disputedPoints: array      ["1b-evaluation"]
    createdAt: string          ISO 8601
```

Single collection, flat documents, JSON primitives only, ISO date strings. Same
rules as `satAttempts` in `sat/js/sat-analytics.js`.
